# 发布基线核对说明

本说明用于避免把官方 Release 名称、Git tag、源码提交和 APK 内版本号混为一谈。

## 强制规则

1. 等官方 GitHub Release 实际发布后再确定个人版本基线，不根据 `upstream/main` 的
   最新提交、发布时间猜测版本号。
2. 以官方 Release 的 tag 为入口，解析 tag 指向的实际提交（peeled commit）。
3. 本地只合并该精确提交，不把“更新到官方最新提交”当作版本同步。
4. 个人 `versionName` 从已经核实的官方 tag 派生，再附加个人后缀；源码中的
   `versionName` 只能作为交叉检查，不能单独决定个人版本名。
5. 构建后读取 APK 自身的 `versionName`、`versionCode`，不能只检查 Gradle 源码。
6. Release 说明必须记录官方 tag、官方提交、个人 tag、个人提交、APK 内版本信息和
   SHA-256。
7. 已公开的 tag 和 APK 不重写；发现说明错误时，在 Release 正文中醒目标注更正。

## 发布前执行

从仓库根目录运行：

```powershell
.\yangyunzhao-fork\仓库维护\Verify-UpstreamRelease.ps1 -UpstreamTag 0.23-preview
```

脚本会校验：

- `upstream` 获取地址是官方仓库，push 地址仍为 `DISABLED`；
- GitHub 上已经存在同名官方 Release；
- 本地 tag 与官方远端 tag 指向同一实际提交；
- 当前 `HEAD` 包含该精确官方提交；
- tag 版本号与该提交源码中的 Android `versionName` 一致。

任一项不满足时默认停止。若官方 tag 与源码版本号确实不一致，先人工检查官方
Release 和官方 APK，记录差异后才可显式放行：

```powershell
.\yangyunzhao-fork\仓库维护\Verify-UpstreamRelease.ps1 `
    -UpstreamTag 0.23-preview `
    -AllowSourceVersionMismatch
```

显式放行只代表“已知并记录这个差异”，不代表源码版本号正确，也不允许据此把个人
版本重新命名成源码中的旧版本。

## 精确同步

脚本输出官方 tag 的完整提交号后，使用该提交号同步，例如：

```powershell
git switch -c sync/upstream-0.23-preview main
git merge --no-ff <脚本输出的完整官方提交号>
```

不要把 `upstream/main` 直接替换到上述命令中。完成冲突审查和测试后，通过个人
仓库 PR 合入 `main`。

## 构建物核对记录

发布前至少保存以下事实：

```text
官方 Release tag:
官方 tag 实际提交:
个人 Release tag:
个人 Release 提交:
APK versionName:
APK versionCode:
APK SHA-256:
```

可使用 Android SDK 的 `apkanalyzer manifest application-id`、
`apkanalyzer manifest version-name`、`apkanalyzer manifest version-code`，或等价的
`aapt dump badging` 检查 APK。最后重新下载 GitHub Release 中的 APK 并复核哈希，
避免本地文件与公开制品不一致。
