## 2. 总体判断

五类限制的性质并不相同：

| 编号 | 限制 | 性质 | 优先级 | 核心结论 |
|---|---|---|---|---|
| S-01 | Release 使用 Android Debug 证书 | 发布身份和长期升级风险 | P0 | 应在用户规模扩大前迁移到专属个人 Release 证书 |
| Q-01 | Release Lint 未执行 | 静态分析工具链阻塞 | P1 | `assembleRelease` 成功不能替代 Lint；应升级兼容工具链并恢复门禁 |
| Q-02 | 完整 JVM 最近仍有 39 项失败 | 测试基线和潜在产品缺陷 | P1 | 不能继续把 39 项全部视为无关噪声，应按三组根因逐项清零 |
| T-01 | 部分异常和生命周期场景未做真机验证 | 验证债务 | P1～P2 | 自动化已有基础，但厂商系统、真实网络和真实 Token 行为仍需用户真机补证 |
| U-01 | 更新检查只指向官方仓库 | 已确认的个人发行功能缺口 | P0～P1 | 只改仓库地址仍不够，还必须修复个人修订号比较和最高版本选择 |

推荐的总体原则：

1. 不改写已经公开的 `0.20-preview-znmlr.1` tag 或 APK；
2. 不再扩大 Debug 证书签名 APK 的长期用户数量；
3. 私钥、口令和真实 OAuth 材料永远不进入 Git、日志、截图或发布说明；
4. 不使用模拟器代替用户真机，真机测试仍由用户控制；
5. 每次给用户的真机指令尽量只有一个小步骤；
6. 不要求第二个账号；已有 Provider 不为异常测试反复删除；
7. 完整测试、Lint、真机和发布结果分别记录，不能互相冒充；
8. 上游 `OpenMinis/OpenMinis` 继续保持只读，不向其推送或创建 PR。

## 3. S-01：Release 构建仍使用 Android Debug 证书

### 3.1 这项限制是什么意思

[Android 构建配置](../../../src/android/app/build.gradle.kts) 中的 `release` 变体已经：

- 启用 R8/ProGuard 压缩和混淆；
- 生成 `app-release.apk`；
- 通过 APK v2 签名和 zipalign 验证。

但同一配置又明确写着：

```kotlin
signingConfig = signingConfigs.getByName("debug")
```

因此，`0.20-preview-znmlr.1` 是 **Release 构建变体**，不是 Debug 构建变体；
但它使用的是 Android Debug 证书，而不是专门用于个人长期发布的生产证书。
“Release 构建”描述构建优化方式，“Release 签名”描述应用身份，两者不能混为一谈。

### 3.2 根因

上游公开源码为了让任何开发者在没有私有 keystore 的情况下也能本地生成 Release
变体，直接复用了 Debug signing config。[BUILDING.md](../../../BUILDING.md) 也明确说明
本地 Release 构建无需额外 keystore。

这适合开发和临时验证，但不适合作为长期个人分发身份。

### 3.3 影响和风险

Android 覆盖安装至少要求：

1. `applicationId` 相同；
2. 新包的 `versionCode` 不低于已安装包；
3. 新旧 APK 的签名身份兼容。

当前风险包括：

- 官方 APK、其他开发者构建和本个人 APK 的证书可能不同，不能互相覆盖；
- 从当前 Debug 证书迁移到个人 Release 证书时，通常需要一次卸载重装；
- 卸载会清除 Provider、Token、会话、设置等本地数据；
- Debug 证书的保管和访问控制不满足长期发布要求；
- 个人 Release 私钥一旦遗失，后续同包名 APK通常无法覆盖升级；
- 个人 Release 私钥一旦泄漏，攻击者可能伪造同签名更新。

默认 Debug keystore 使用公开的默认口令，并不等于任何人都拥有本机那一份私钥，
但这仍然不是合格的长期发布策略。

### 3.4 已发布 `.1` 的处理原则

已经公开的 `.1` 不能通过重新打包同名 APK、移动 tag 或替换资产来“静默修复”。
正确做法是：

1. 保留 `.1` 的 tag、源码、哈希和原始发布说明；
2. 后续在 `.1` Release 顶部增加“Debug 证书签名，已被新版本替代”的提示；
3. 从新的个人版本开始永久使用同一把个人 Release key；
4. 把首次签名迁移导致的卸载和数据风险写入中文发布说明。

### 3.5 推荐解决方案

#### S0：用户决策和冻结

需要用户确认：

- 是否从下一版本开始永久迁移到专属个人 Release key；**建议确认**；
- 是否接受一次卸载重装，还是先实现重要数据的导出和恢复；
- keystore 的唯一责任人和保管位置；
- 是否先只在本地人工签名；**建议暂不把私钥放入 GitHub Actions**。

在完成决策前，不继续发布更多 Debug 证书签名 APK。

#### S1：建立个人签名身份

在仓库外离线生成长期个人 app-signing keystore：

- 使用强随机口令；
- 使用足够长的有效期；
- 构建用副本放在仓库外，并限制 Windows 文件权限；
- 制作两份相互独立的加密离线备份；
- 至少完成一次从备份恢复并重新验签的演练；
- 记录证书 SHA-256 指纹；指纹可以公开，私钥和口令不能公开。

不得把 keystore、口令、真实路径或包含口令的 properties 文件加入 Git。

#### S2：Gradle 采用失败关闭

新增独立 `release` signing config：

- 从明确命名的环境变量或仓库外本地配置读取 store path、alias 和口令；
- 请求 Release 构建时，四项配置缺一即明确失败；
- 不允许缺少配置时自动回退到 Debug 证书；
- Debug 构建继续使用 Debug key；
- 在构建文档中只提供占位符示例；
- 为本地签名配置增加精确 `.gitignore` 规则。

#### S3：静态验签

每个候选 APK 必须执行：

- `assembleRelease`；
- `apksigner verify --verbose --print-certs`；
- `zipalign -c`；
- `aapt dump badging`；
- ABI、版本名、版本代码和 SHA-256 核对；
- `signingReport` 指纹核对；
- Git 跟踪文件和差异的敏感信息扫描。

Release 指纹必须等于登记的个人证书，并且不等于 Android Debug 指纹。

#### S4：真机签名迁移

1. 用户先备份数据或明确确认数据可以丢弃；
2. 验证 `.1` 无法直接覆盖新证书版本是预期行为；
3. 用户明确同意后卸载 `.1` 并全新安装新证书版本；
4. 使用同一生产证书再构建后续候选；
5. 验证新证书版本之间可以覆盖升级，并保留 Provider 和设置。

#### S5：发布和运维

- 新版本中文说明写明证书指纹、一次性迁移、APK 哈希和数据风险；
- 不改写 `.1` tag；
- 从 GitHub 重新下载 APK，再验签和验哈希；
- 后续每次发布使用同一把个人 key；
- 定期检查备份是否仍可恢复；
- 任何 key rotation 都单独评审，不临时换 key。

### 3.6 验收标准

- Release 配置不再引用 Debug signing config；
- Release 缺少签名配置时明确失败，不产生 Debug 签名的 Release APK；
- Debug 构建仍能正常完成；
- Git 中没有 keystore、口令或真实签名配置；
- Release APK 验签和 zipalign 通过；
- 证书 SHA-256 与公开登记值一致；
- 新证书版本全新安装成功；
- 同一新证书的后续版本覆盖成功且测试数据保留；
- 中文说明对 `.1` 的一次性迁移风险表述准确。

## 4. Q-01：Release Lint 未执行

### 4.1 这项限制是什么意思

当前配置包含：

```kotlin
checkReleaseBuilds = false
disable += "NonNullableMutableLiveData"
```

`checkReleaseBuilds = false` 会让 Release 构建跳过 `lintVitalAnalyzeRelease`。
因此，`assembleRelease` 成功只能证明编译、资源处理、原生构建、R8 和打包完成，
不能证明 Release Lint 通过。

### 4.2 根因

当前主要工具链为：

- Android Gradle Plugin 8.7.3；
- Kotlin 2.1.0；
- KSP 2.1.0-1.0.29；
- Gradle 8.11.1；
- JDK 17；
- `compileSdk = 36`。

[第零阶段基线验收报告](../../功能/OpenAI设备码登录/验收/第零阶段基线验收报告.md)记录，Lint 在规则禁用列表生效前
就于 detector dispatch 阶段抛出 `IncompatibleClassChangeError`：

- 主代码分析曾由 `NonNullableMutableLiveDataDetector` 触发；
- AndroidTest 和 UnitTest 分析曾由 `FrequentlyChangingValueDetector` 触发；
- 后续 UnitTest 首触发 detector 又变为 `RememberInCompositionDetector`。

这说明问题属于 Android Lint 与 Kotlin Analysis API 的工具链不兼容或组合缺陷，
而不是简单禁用某一条规则就能解决。

同时，API 36 对 AGP 有更高兼容要求。实施升级时应以当时的官方兼容说明为准：

- [Android Gradle Plugin 兼容说明](https://developer.android.com/build/releases/about-agp)
- [AGP 8.10 发布说明](https://developer.android.com/build/releases/agp-8-10-0-release-notes)
- [AGP 8.8 发布说明](https://developer.android.com/build/releases/past-releases/agp-8-8-0-release-notes)

当前可优先试验 AGP 8.10 的最新兼容补丁，因为它与现有 Gradle 8.11.1 对齐；
但“升级一定修复本项目”只是待验证假设，不能提前写成事实。

### 4.3 影响

- Lint 没有完成全量分析，不能声称“0 个 Lint 问题”；
- 工具崩溃不等于代码没有静态缺陷；
- Lint 未完成时，剩余问题数量和严重性未知；
- 继续关闭 Release Lint 会让未来发布缺少静态分析门禁；
- 即使编译、测试和真机通过，也不能替代 Lint 的资源、Manifest、API 和 Compose
  等检查。

### 4.4 解决计划

#### L0：重新冻结当前证据

在当前 `main` 上分别执行：

- `lintDebug --stacktrace`；
- `lintRelease --stacktrace`；
- 记录工具链版本、失败任务、首个 detector、异常类型和关键堆栈；
- 将日志和摘要放入新的验收文档，避免只保留口头结论。

如果实际结果与历史记录不同，以新的证据为准，不强行凑成原有失败签名。

#### L1：隔离试验最小工具链升级

在独立分支或独立工作树中：

1. 先把 AGP 升级到与 API 36 兼容的 8.10 最新补丁；
2. 暂不同时升级 Kotlin、KSP 和 Compose；
3. 只有出现明确兼容要求时，才做最小联动升级；
4. 执行 Gradle 配置、完整 JVM、`lintDebug`、`lintRelease`、
   `assembleDebug` 和 `assembleRelease`；
5. 若仍崩溃，记录候选版本矩阵并停止合入。

不得仅因为“版本已升级”就判定问题解决。

#### L2：处理 Lint 真正报告的问题

工具不再崩溃后：

- 逐项理解并修复 Lint issue；
- 不能修复但确需延期的项目，才进入窄范围 baseline；
- 每个 baseline 项都记录原因、风险和复查条件；
- 不使用 `abortOnError=false`、大范围 disable 或把崩溃结果写入 baseline。

#### L3：恢复 Release 门禁

- 删除 `checkReleaseBuilds = false`，恢复默认或显式设为 `true`；
- 只有确认 detector 已能正常运行后，再决定是否移除单条 disable；
- 确认 `assembleRelease` 实际触发并通过 `lintVitalAnalyzeRelease`；
- 将完整 Lint 纳入个人发布前检查。

### 4.5 验收标准

- `lintDebug` 和 `lintRelease` 均完整结束，不再抛 Analysis API/ICCE；
- 主代码、AndroidTest、UnitTest 三类分析任务均完成；
- 新出现的 Lint issue 已逐项处理或有窄范围、可追踪的延期；
- `checkReleaseBuilds` 已恢复；
- `assembleRelease` 实际执行并通过 vital Lint；
- JVM 测试和 Debug/Release 构建没有因工具链升级出现新增回归。

## 5. Q-02：完整 JVM 回归最近仍有 39 项失败

### 5.1 这项限制是什么意思

最近一次完整 JVM 历史结果是：

```text
471 tests completed, 39 failed, 0 errors
```

本次版本发布只修改 `versionName`、`versionCode` 和中文注释，因此当时选择执行
66 项设备码聚焦测试和完整 Release 构建，没有再次运行完整 JVM 套件。

这可以解释为什么没有重跑，却不能证明当前 tag 的完整测试仍然精确等于
`471 / 39`，更不能证明完整套件已经通过。当前磁盘测试报告已被后来的 66 项
聚焦测试覆盖，所以 `471 / 39` 只能作为历史证据使用。

### 5.2 39 项失败不能全部视为无关噪声

#### A. AnthropicProviderTest：24 项

公开仓库缺少私有 `ANTHROPIC_OAUTH_IDENTIFIER_PROMPT`。进一步代码审查发现，
`AnthropicProvider.resolveSystemPrompt()` 可能在判断是否属于 OAuth 路径前，
就无条件读取该私有值。

这意味着它不一定只是“测试环境没配置”，也可能暴露公开构建中 Anthropic
API Key 路径对私有 OAuth 配置的错误耦合。

解决方向：

- 仅在 OAuth 分支延迟读取该前缀；
- 或注入 OAuth prefix provider；
- 测试只使用非秘密假值；
- 不把真实私有 prompt 提交进仓库。

#### B. OpenAIProviderTest：11 项

测试使用本机 MockWebServer，但 Provider 内部固定创建默认 OkHttpClient。
历史环境中的系统代理可能截获 localhost 请求，最后表现为：

```text
TransientError: Server returned an empty response
```

这更像测试隔离不足，不能直接证明真实 OpenAI 请求实现错误。

解决方向：

- 给 Provider 增加仅供内部或测试使用的 client/client factory 注入；
- MockWebServer 测试客户端强制使用 `Proxy.NO_PROXY`；
- 生产默认客户端继续保留现有系统代理行为；
- 测试过程中不连接真实外网。

#### C. TerminalSanitizerTest：4 项

实现当前可能直接取最后一个非空 CR 片段，而测试期望终端式覆盖后保留旧行未被
覆盖的后缀，例如：

```text
AAAA\rBB  →  BBAA
```

另外，最终 `.trim()` 可能删除 wget 输出或进度文本中有意义的首尾空格。
这是实现与期望语义不一致，可能影响真实终端输出，不能直接把测试期望改成现状。

解决前应先对照：

- iOS 实现；
- 真实终端样本；
- CR、CRLF、短覆盖、长覆盖和空格边界的产品预期。

### 5.3 解决计划

#### J0：重新运行完整基线

在当前 `main` 上执行完整 `testDebugUnitTest`：

- 保存完整 XML 和 HTML；
- 导出失败测试全名；
- 记录异常类型和规范化签名；
- 同时记录提交哈希和工具链版本；
- 不再只比较失败总数。

如果当前测试总数或失败数不是 `471 / 39`，按新事实更新文档。

#### J1：分三组修复

建议拆成三个小提交：

1. 修复 Anthropic 非 OAuth 路径的私有配置耦合；
2. 为 OpenAI MockWebServer 测试建立无代理的可注入客户端；
3. 确认 Terminal CR/空格规范后修正实现和边界测试。

每组都先运行直接相关测试，再运行设备码聚焦回归。

#### J2：完整 JVM 清零

- 在整合提交上运行完整套件；
- 建议连续运行两次，排除偶发顺序或端口问题；
- 最终以“当前实际 N 项、0 failed、0 errors”为验收结果；
- 保存规范化测试摘要，避免后续聚焦测试覆盖证据。

### 5.4 验收标准

- Anthropic API Key 和 OAuth 两条路径均有独立测试；
- 测试不需要真实私有配置；
- MockWebServer 在存在或不存在系统代理时都只访问 localhost；
- Terminal Sanitizer 的 CR 和空格语义已有明确规范；
- 相关测试不访问真实 AI 服务；
- 完整 JVM 连续两次 0 失败、0 错误；
- 设备码核心和刷新聚焦测试继续全绿。

## 6. T-01：部分真机场景尚未完整执行

### 6.1 这项限制是什么意思

这不是已经确认的产品缺陷，而是：

> 自动化已经覆盖核心协议和并发逻辑，但 Android 真机、厂商系统、真实网络切换、
> 锁屏深度睡眠和真实 Token 生命周期仍缺少完整证据。

现有自动化已经覆盖：

- 取消和有限重试；
- 请求与轮询网络失败；
- generation 和迟到结果隔离；
- Activity/进程重建回到安全初始状态；
- Token 刷新成功、拒绝、并发轮换和比较后删除。

但 JVM 和 MockWebServer 无法代替真实 OEM 后台限制、锁屏、网络切换和真实
OpenAI Token 刷新。

### 6.2 各未执行场景的具体含义

#### 取消后重试

需要证明旧 attempt 被取消后：

- 用户能立即开始新 attempt；
- 旧网页或迟到轮询不能认证新 attempt；
- 不会保存半套 Provider 或旧 Token。

#### 网络异常

需要分别观察请求设备码阶段和轮询阶段：

- 断网、DNS 失败和超时不会导致崩溃；
- 重试次数有限；
- 最终会明确停止而不是永久加载；
- 网络恢复后可以重新开始；
- 日志不包含授权码或 Token。

#### 旋转

旋转可能触发 Activity 配置重建。需要确认：

- 不会重复打开浏览器；
- 不会重复创建请求；
- 同一 attempt 的状态保持一致，或按设计明确终止；
- 不会产生重复 Provider。

#### 后台和锁屏

需要确认应用切后台或锁屏解锁后：

- 轮询和倒计时状态可解释；
- 不重复发起网络请求；
- 不泄露一次性授权信息；
- 回到前台后能够继续或明确重新开始。

#### 进程重建

“划掉最近任务”不一定等于系统真正杀死进程。彻底进程死亡需要单独确认安全复现
方法。预期行为是：

- 新进程回到 Idle；
- 不恢复授权码、PKCE 或 Token；
- 不自动继续旧轮询；
- 旧任务不能迟到写入 Provider。

#### 自然 Token 刷新

当前刷新不是后台定时执行，而是在模型请求调用 `validAccessToken()` 时按需判断。
当 `expire_at` 距当前小于四小时时，才进入刷新路径。

此前真实最小请求可能触发过刷新，也可能没有；在没有安全诊断事件的情况下，
不能仅凭“收到模型响应”倒推自然刷新已经通过。

### 6.3 既定安全边界

- 不启动模拟器；
- 由用户使用自己的真机；
- 临近具体场景时再讨论安全步骤；
- 每次只给用户一个小步骤；
- 不要求第二账号；
- 已有 Provider 不为测试切换登录方式；
- 临时设备码测试从“新建 Provider”进入，未保存就退出；
- 授权码、Token、PKCE、凭据 JSON不得进入反馈、截图或日志；
- 任何可能影响紧急通信、设备设置或数据的操作，先停止并确认。

### 6.4 解决计划

#### T0：本地准备

- 固定待测 tag、APK SHA-256 和签名身份；
- 保留现有 Provider 和应用数据；
- 建立“一场景一记录”模板；
- 明确停止条件和脱敏规则；
- 如需证明刷新，只增加 `refresh started/succeeded/failed` 这类无敏感值诊断事件；
- 不记录请求体、响应体、URL 参数、Token、Token 哈希或账号标识。

#### T1：低风险生命周期场景

由用户用同一账号、一次一个场景测试：

1. 取消后重新开始；
2. 旋转；
3. 切后台再返回；
4. 锁屏再解锁。

每轮使用未保存的临时尝试，结束时取消，并确认列表中没有临时 Provider。

#### T2：网络场景

执行前再与用户讨论，不默认开启飞行模式。优先在可控测试 Wi-Fi 上短暂断开，
避免影响紧急通信。

分别验证请求阶段和轮询阶段：

- 有限重试；
- 明确失败或取消；
- 恢复后可新建尝试；
- 无崩溃、永久加载、空凭据或半套 Provider。

#### T3：Activity 和进程场景

- 普通 Activity 重建先由旋转覆盖；
- 彻底进程死亡的复现方式另行确认；
- 如果方法可能影响设备设置或数据，停止并继续标记为“未执行”；
- 不把“划掉最近任务”错误记录为进程死亡验收。

#### T4：自然 Token 刷新长期观察

- 继续使用现有已保存 Provider，不新增账号；
- 在加入无敏感信息的刷新事件后等待自然刷新窗口；
- 用户明确同意可能产生少量用量后，发送一次最小请求；
- 同时验证刷新事件、请求成功和重启后 Provider 仍可用；
- 只有模型响应、没有刷新事件时，不算刷新通过。

#### T5：缺陷闭环

发现以下任一情况立即停止：

- 崩溃；
- 凭据或授权码泄漏；
- 旧 attempt 写入；
- 重复 Provider；
- 进程重建恢复敏感授权信息；
- 网络恢复后仍永久卡住。

修复后先重跑相关 JVM 测试和 Release 构建，再由用户复测。

### 6.5 验收标准

| 场景 | 验收标准 |
|---|---|
| 取消 | 显示取消而非认证失败；可立即新建 attempt；旧结果不能写入 |
| 网络 | 有限重试并停止；恢复后可重试；无崩溃、无限加载或半套 Provider |
| 旋转 | 状态一致或明确终止；不重复浏览器、请求、授权信息或 Provider |
| 后台/锁屏 | 返回后状态可解释；无重复请求或敏感信息泄漏 |
| 进程死亡 | 新进程回到 Idle；不恢复授权码/PKCE/Token；旧任务不能写入 |
| 自然刷新 | 明确刷新成功事件、最小请求成功、重启后仍可用，且无敏感日志 |

无法安全执行的项目继续标记“未执行”，不能用 JVM 结果代替真机通过。

## 7. U-01：更新检查只指向官方仓库

### 7.1 这项限制是什么意思

[UpdateChecker](../../../src/android/app/src/main/java/com/openminis/app/data/UpdateChecker.kt)
把以下内容硬编码为官方仓库：

- `OWNER = "OpenMinis"`；
- `REPO = "OpenMinis"`；
- `RELEASES_URL` 指向官方 Releases。

因此，个人版本不会读取 `yangyunzhao/OpenMinis` 的 Release。

### 7.2 只修改仓库地址仍然不够

当前 `normalizeTag()` 会在第一个 `-` 处截断：

```text
0.20-preview-znmlr.1  →  0.20
0.20-preview-znmlr.2  →  0.20
```

所以即使把请求地址改成个人仓库，`.1` 仍然无法判断 `.2` 比自己新。

另外还存在两个相关问题：

1. Pending update 目前保存的是归一化后的数字版本，无法区分 `.1` 和 `.2`；
2. 最高版本选择使用
   `compareBy { compareVersions(it.versionName, "0") }`，把与 `0` 比较得到的
   `-1 / 0 / 1` 当成排序 key，多数正常版本都会得到 `1`，不能可靠选出最高版本。

文件头关于 RC 后缀排序的注释也与当前“删除全部后缀”的实际行为不一致。

### 7.3 当前 `.1` 的不可逆启动问题

已经发布的 `.1` 本身没有个人更新源逻辑，因此它不可能自动发现未来 `.2`。
修复代码只能进入新的 APK：

- `.1` 用户至少需要手动安装一次新版本；
- 新版本修复更新检查后，才能从该版本开始自动发现后续个人 Release。

如果新版本同时完成个人 Release key 迁移，`.1` 还会因为签名变化无法覆盖，
需要按 S-01 计划先备份并卸载。这不是更新检查代码可以绕过的 Android 安全规则。

因此推荐：

1. 新证书签名的 `.2` 作为一次性人工迁移版本；
2. `.2` 内已经包含个人更新源和正确版本比较；
3. 用同一生产证书发布 `.3`；
4. 真正验收 `.2 → .3` 的应用内无损升级链。

不应为了测试 `.1 → .2` 自动覆盖而继续扩大 Debug 证书发布。

### 7.4 解决计划

#### U0：更新源配置化

- 把 owner、repo 和 Releases URL 集中为 BuildConfig 或单一配置；
- 个人构建指向 `yangyunzhao/OpenMinis`；
- 上游构建仍可配置官方源；
- 不在多处散落硬编码；
- 个人版本只消费个人仓库附带的 APK，不混装官方 APK。

#### U1：建立纯版本模型

解析并保留：

- 可选 `v` 前缀；
- 数字基线；
- `preview` 渠道；
- `znmlr` 发行标识；
- 个人修订号。

比较规则至少满足：

- `0.21` 高于 `0.20`；
- 同一数字基线下 `.2` 高于 `.1`；
- 同一版本相等；
- 同基线官方 `0.20-preview` 不得使本地个人 `.1` 降级；
- 未知或畸形 tag 跳过或保守判为不可更新；
- 使用真正的两两 Comparator 选择最高版本。

#### U2：保留完整版本身份

以下位置都保存完整规范版本：

- `CheckResult`；
- 下载文件名；
- Pending update；
- 恢复安装逻辑；
- 用户界面。

安装到 `.2` 后，对应 `.2` 的 pending 应被清理，不能只比较成 `0.20`。

#### U3：自动化测试

将版本解析、比较和 Release 选择抽为纯函数或可注入组件，至少覆盖：

- `.2 > .1`；
- `.1 < .2`；
- 同版本相等；
- `v` 前缀等价；
- `0.21-preview-znmlr.1` 高于全部 `0.20` 个人修订；
- 同基线官方 preview 不覆盖个人版；
- draft 忽略、个人 prerelease 接受；
- 无 APK、畸形 tag；
- GitHub 返回顺序打乱后仍选语义最高且有目标 APK的版本；
- pending 在旧版本可恢复，在目标版本自动清理；
- API 和浏览器链接全部指向个人仓库。

测试使用 MockWebServer，不访问真实 GitHub。

#### U4：构建和发布

- 完整 JVM 和更新专项测试通过；
- 构建 Release APK；
- 验证签名、zipalign、版本、ABI 和 SHA-256；
- 新版本只附一个目标 `arm64-v8a` APK；
- 中文说明写清个人仓库、签名迁移和应用内更新的起始版本。

#### U5：真机端到端

首次签名迁移完成后：

1. 真机安装新证书 `.2`；
2. 使用同一证书发布 `.3`；
3. 在 `.2` 中点击检查更新；
4. 应明确发现 `.3`；
5. 下载并覆盖安装；
6. 关于页显示 `.3`；
7. Provider、会话和设置保留；
8. 再次检查时显示已是最新。

### 7.5 验收标准

- 更新 API 和手动链接只指向 `yangyunzhao/OpenMinis`；
- `.1 → .2` 在纯版本比较中为 UpdateAvailable；
- `.2 → .1` 和 `.2 → .2` 为 UpToDate；
- `0.21-preview-znmlr.1` 高于任意 `0.20` 个人修订；
- 打乱 GitHub Release 顺序仍选出语义最高、含目标 APK的版本；
- pending 保存完整后缀并正确失效；
- Mock/JVM、Release 构建、签名和哈希检查通过；
- 真机 `.2 → .3` 同签名覆盖成功且数据不丢；
- 安装后不会重复提示同一版本。

## 8. 总体实施顺序

| Phase | 主要任务 | 依赖 | 主要验收 |
|---|---|---|---|
| R0 | 冻结 `.1` 证据和本文档 | 无 | tag、APK 哈希、已知限制不被改写 |
| R1 | 重跑完整 JVM 和 Lint 堆栈，建立当前证据 | R0 | 当前实际失败清单和工具链异常可复现 |
| R2 | 用户决定个人 Release key 和数据迁移方式 | R0 | 密钥责任、备份、迁移和本地签名策略明确 |
| R3A | 清零三组 JVM 失败 | R1 | 完整 JVM 连续两次 0 失败 |
| R3B | 试验兼容 AGP，恢复完整 Lint | R1 | Debug/Release Lint 完整结束，Release 门禁恢复 |
| R4 | 实现个人更新源和个人版本比较 | R1 | 更新专项测试全绿，完整版本身份不丢失 |
| R5 | 建立个人签名配置并构建 `.2` 候选 | R2、R3A、R3B、R4 | 生产证书验签、完整质量门禁通过 |
| R6 | 用户完成一次性 `.1 → .2` 人工迁移 | R5 | 全新安装成功，核心功能和数据策略符合预期 |
| R7 | 补齐低风险真机场景和自然刷新观察 | R6 | 各场景逐项通过或如实保留未执行 |
| R8 | 同证书发布 `.3` 并验收应用内更新 | R6、R7 | `.2 → .3` 自动发现、覆盖安装、数据保留 |

其中 R3A、R3B 和 R4 在资源允许且不写同一构建输出目录时可以并行调查或分支开发；
最终必须在同一整合提交上重新执行完整验证。

## 9. 发布门禁

下一次个人公开发布前，至少满足：

- [ ] 已决定并建立长期个人 Release key；
- [ ] 私钥和口令没有进入 Git、日志或构建产物；
- [ ] 当前完整 JVM 套件 0 失败、0 错误；
- [ ] `lintDebug` 和 `lintRelease` 完整结束；
- [ ] `checkReleaseBuilds` 已恢复；
- [ ] 设备码聚焦测试继续全绿；
- [ ] 个人更新源和 `znmlr` 修订号比较测试通过；
- [ ] `assembleRelease`、R8、apksigner、zipalign、ABI 和 SHA-256 通过；
- [ ] tag 指向已合入个人 `main` 的提交；
- [ ] GitHub 重新下载的 APK 与本地产物哈希一致；
- [ ] 中文发布说明写明签名、迁移、架构、系统要求和未执行验证；
- [ ] 官方上游仍没有个人 tag、PR 或推送。

如果任一门禁没有执行，发布说明必须明确保留对应限制，不能以“暂时没有发现问题”
替代验证结果。

## 10. 需要用户确认的决策

实施代码前需要用户依次确认：

1. 是否接受从下一版本开始永久使用个人 Release key；
2. 是否需要先实现应用数据导出/恢复，还是接受一次卸载清除数据；
3. keystore 的责任人、两份离线备份位置和恢复演练方式；
4. 是否继续采用本地人工签名，暂不把私钥放入 GitHub Actions；
5. 何时进入用户真机场景测试；届时仍按“一次一个小步骤”执行。

这些决策不阻止继续进行只读调查、测试基线复核或工具链实验，但会阻止新的个人
Release 正式发布。
