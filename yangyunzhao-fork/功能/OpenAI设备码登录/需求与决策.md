## 2. 背景与目标

OpenMinis 当前在 Android 上通过浏览器完成 OpenAI/ChatGPT OAuth 登录，并依赖：

```text
http://localhost:1455/auth/callback
```

部分手机、浏览器、代理或系统环境不能正确处理该回调，导致用户已经在网页完成登录，但授权结果无法返回 OpenMinis。

本需求的目标是：

> 为 Android 端 OpenAI OAuth 增加不依赖手机本地端口和 `localhost` 回调的设备码登录，同时保留全部现有登录方式、凭据刷新能力和 Provider 行为。

## 3. 已调查的事实基线

### 3.1 当前 OpenMinis

- OpenAI 浏览器回调登录位于：
  - `src/android/app/src/main/java/com/openminis/app/auth/OpenAIOAuthManager.kt`
  - `src/android/app/src/main/java/com/openminis/app/auth/OAuthCallbackServer.kt`
- 添加 Provider 的 OAuth UI 位于：
  - `src/android/app/src/main/java/com/openminis/app/ui/settings/AddProviderScreen.kt`
- 已保存 Provider 的重新登录 UI 位于：
  - `src/android/app/src/main/java/com/openminis/app/ui/settings/ProviderDetailScreen.kt`
- Kimi 已有设备码登录的 UI、轮询、取消和测试先例：
  - `auth/KimiDeviceFlow.kt`
  - `auth/KimiOAuthManager.kt`
  - `ui/settings/KimiDeviceLoginDialog.kt`
  - `KimiDeviceFlowTest.kt`
- OpenAI OAuth 已有凭据存储、自动刷新、静态模型列表和导入导出路径。

Kimi 的 UI 和生命周期结构可以参考，但它使用 RFC 8628 风格协议，不能直接作为 OpenAI 网络协议实现。

### 3.2 当前官方 Codex 设备授权

本机 Codex CLI `0.145.0` 已提供：

```text
codex login --device-auth
```

官方文档将设备码登录标记为 beta，并要求个人账户在 ChatGPT 安全设置中启用，或由 workspace 管理员允许。

当前官方 Codex 源码使用自定义设备授权流程，不是标准 RFC 8628：

1. 请求用户码：
   - `POST {issuer}/api/accounts/deviceauth/usercode`
   - JSON 请求包含 `client_id`
2. 响应包含：
   - `device_auth_id`
   - `user_code`
   - `interval`
3. 用户打开：
   - `{issuer}/codex/device`
4. 应用轮询：
   - `POST {issuer}/api/accounts/deviceauth/token`
   - JSON 请求包含 `device_auth_id` 和 `user_code`
5. 成功后先得到：
   - `authorization_code`
   - `code_challenge`
   - `code_verifier`
6. 再以 `{issuer}/deviceauth/callback` 作为 `redirect_uri` 交换 OAuth Token。
7. 当前官方实现最长等待 15 分钟，并主要把轮询的 HTTP 403/404 视为继续等待。

因此，产品需求可以继续使用“设备码登录”这一用户概念，但技术实现不得假设服务端一定返回标准的 `device_code`、`expires_in`、`authorization_pending`、`slow_down`、`access_denied` 或 `expired_token`。

上述端点和字段来自当前官方 Codex 实现，不应被视为 OpenAI 已承诺长期兼容的公开集成 API。实现前后都应重新核实当前 Codex 源码和可用行为。

## 5. 用户故事

- 作为无法使用 `localhost` 回调的 Android 用户，我希望通过登录网址和一次性授权码完成 ChatGPT/OpenAI 授权。
- 作为普通用户，我希望能够打开或复制登录网址，并原样复制授权码。
- 作为等待授权的用户，我希望 OpenMinis 自动检查结果，而不是反复手动刷新。
- 作为想中止登录的用户，我希望取消后立即回到未登录状态，并能重新开始。
- 作为遇到过期、网络错误或功能不可用的用户，我希望看到易懂提示，并能重试或改用浏览器回调。
- 作为已有 OpenAI Provider 的用户，我希望升级后无需重新登录，现有模型、会话和自动刷新继续可用。

## 6. 功能需求

### FR-01 登录方式选择

新增 OpenAI Provider 页面中的 OAuth 配置区域应清楚区分：

1. 设备码登录；
2. 现有浏览器回调登录；
3. 手动配置 Bearer Token。

必须保留现有浏览器回调登录。设备码登录应优先展示，但“默认选择、排序靠前或推荐标签”的具体形式由 `D-01` 决定。

已保存 Provider 的详情页不增加设备码重新授权入口；需要改用设备码时，按 `D-02` 删除旧 Provider 后重新新建。

### FR-02 请求授权信息

用户选择设备码登录后，OpenMinis 应：

1. 防止重复点击创建多个并发请求；
2. 按当前官方 Codex 流程请求授权信息；
3. 校验服务端必需字段；
4. 将服务端返回的 `user_code` 原样交给 UI；
5. 不假设授权码长度、大小写、字符集或连接符格式；
6. 校验最终展示给用户的授权码和登录网址均非空且可用；
7. 服务端字段或协议变化时给出可理解错误，不保存半套状态。

### FR-03 展示、打开和复制

等待授权界面至少应包含：

- 登录网页地址；
- 一次性授权码；
- “打开登录网页”按钮；
- “复制登录网址”按钮；
- “复制授权码”按钮；
- 当前等待状态；
- 取消按钮。

用户复制网址或授权码后应得到明确反馈。浏览器打开方式由 `D-03` 决定，但无论采用 Custom Tab 还是外部默认浏览器，都必须保留复制网址能力。

面向普通用户的界面文案不得要求用户理解 OAuth、PKCE、Access Token、Refresh Token 等技术术语；必要的故障说明应转换为清楚、可操作的普通语言。

### FR-04 自动等待授权

显示授权码后，OpenMinis 应自动等待授权结果：

- 遵守服务端返回的轮询间隔；
- 不要求用户反复点击“检查状态”；
- 不因临时等待显示永久、无说明的加载状态；
- 不依赖手机本地端口或 `localhost` 回调；
- 达到当前协议允许的最长等待时间后结束本次尝试；
- 协议响应语义以当前官方 Codex 行为为准，不伪造服务端未提供的拒绝或过期状态。

### FR-05 授权被拒绝或明确失败

如果服务端能够明确表示用户拒绝授权或本次授权失败，OpenMinis 必须：

- 立即停止当前等待；
- 使用普通用户能够理解的语言说明授权未完成；
- 清理本次临时状态；
- 不保存 Provider、Token 或其他不完整凭据；
- 保留重新登录及改用浏览器回调登录的入口。

只有当前协议确实无法区分“仍在等待”和“用户已拒绝”时，才允许继续等待到其他明确终止信号或本次登录超时。

### FR-06 登录成功

授权成功后，OpenMinis 应：

1. 完成授权码到 OAuth Token 的交换；
2. 复用现有安全凭据存储；
3. 按当前官方协议和现有 OpenAI OAuth 数据模型，保存登录与刷新所需的有效凭据；
4. 识别 OpenAI OAuth 已成功；
5. 清除授权码、设备授权 ID、PKCE 等临时状态；
6. 允许保存当前 Provider；
7. 继续使用现有自动刷新机制；
8. 能够选择可用模型、创建会话并发起请求；
9. 应用重启后保持有效登录状态。

模型加载失败是否影响“登录成功”的判定，见 `D-07`。

### FR-07 取消

等待期间用户可以取消。取消后必须：

- 停止或使当前轮询失效；
- 清理本次临时状态；
- 返回未登录状态；
- 允许立即重新登录；
- 不把主动取消显示为登录失败；
- 忽略旧任务的迟到结果；
- 不覆盖后续新任务的状态和凭据。

如果服务端没有撤销授权码的接口，“授权码不再使用”定义为客户端不再轮询、交换或接受其结果，不承诺服务端立即销毁该授权码。

### FR-08 超时和重新登录

达到当前官方流程规定的等待上限后：

- 停止等待；
- 提示授权码已过期或本次登录已超时；
- 清理临时状态；
- 允许获取新的授权码；
- 重新登录必须向服务端发起新的授权请求，并展示该次请求返回的新授权码；
- 已过期、已使用或属于旧尝试的授权码不得再次轮询、交换或显示为当前有效码；
- 新旧登录尝试必须具有不可混淆的本地身份，例如 attempt ID、generation token 或独立 session object；
- 旧任务的结果不得写入新任务。

### FR-09 功能未启用或不可用

设备码登录可能被个人安全设置、workspace 管理员、区域或服务状态禁用。

当服务端明确表示功能未启用或不支持时，应：

- 说明当前无法使用设备码登录；
- 提示检查 ChatGPT 安全设置或联系 workspace 管理员；
- 提供现有浏览器回调登录入口；
- 保留重新尝试的能力；
- 不影响 API Key、Bearer Token 和其他 Provider。

### FR-10 网络异常

请求用户码、轮询、最终 Token 交换和登录后模型加载均可能失败。

应用必须：

- 不崩溃、不永久加载；
- 不保存无效 Provider 或半套凭据；
- 给出面向普通用户的网络或代理提示；
- 保留重试入口；
- 不直接展示内部堆栈、Token 响应正文或敏感字段。

短暂断网是继续重试还是立即结束，由 `D-04` 决定。

### FR-11 Provider 生命周期

- 登录成功后、Provider 保存前离开页面时，不得永久遗留孤立凭据；
- Provider 保存失败时不得留下无法管理的凭据；
- 模型刷新失败不得破坏已经成功保存的有效凭据；
- 删除 OpenAI OAuth Provider 时必须同时清理该实例的 API Key 镜像和完整 OAuth 凭据，不得遗留无法管理的旧 Token；
- 已保存 Provider 的编辑、删除、导入导出和退出登录不得回归；
- 现有 OpenAI OAuth Provider 升级后继续可用，无需统一重新登录。

## 7. UI 状态模型

| 状态 | 用户可见反馈 | 可执行操作 | 退出条件 |
|---|---|---|---|
| `idle` | 尚未开始 | 选择设备码或浏览器登录 | 用户开始登录 |
| `requestingCode` | 正在请求授权信息 | 取消 | 成功或请求失败 |
| `waitingForUser` | 显示网址、原样授权码和等待提示 | 打开、复制、取消 | 授权完成、超时或错误 |
| `exchangingToken` | 正在完成登录 | 取消是否允许见实现调查 | 成功或失败 |
| `authenticated` | 登录成功 | 保存 Provider | 保存、离页或退出登录 |
| `cancelled` | 已取消，不显示失败 | 重新登录 | 新尝试开始 |
| `expired` | 本次登录已超时 | 重新登录 | 新尝试开始 |
| `networkError` | 网络或代理错误 | 重试、改用浏览器登录 | 用户选择 |
| `authFailed` | 授权未完成或交换失败 | 重试、改用浏览器登录 | 用户选择 |
| `unsupported` | 功能未启用或不支持 | 检查设置、浏览器登录、重试 | 用户选择 |

状态名称是需求层术语，不强制代码采用相同枚举名。

## 8. 生命周期与并发

### LIFE-01 单一有效尝试

同一个 Provider 实例同一时间只能有一个有效登录尝试。新尝试开始时，旧尝试必须取消或失效。

### LIFE-02 迟到结果保护

每次登录必须具有不可混淆的本地尝试身份，例如 attempt ID、generation token 或独立 session object。任何网络响应、轮询成功或 Token 持久化前，都应确认当前尝试仍然有效。

### LIFE-03 Android 生命周期

最低要求：

- 切到后台再返回后，当前登录不会错误完成或覆盖其他尝试；
- 锁屏再解锁后，状态保持一致或明确结束；
- 离开当前页面时不会产生孤立凭据；
- Compose 重组不会重复启动网络请求。

按已确认的 `D-05`：切到后台、锁屏、旋转和 Activity 重建后应保持正确状态，不重复启动或混淆登录任务；如果系统彻底杀死进程，则不持久化或恢复旧授权码，用户重新发起登录。不得把授权码或 Token 放入普通 Bundle、`rememberSaveable`、明文数据库或日志。

### LIFE-04 可取消网络操作

仅取消 Compose `Job` 不足以证明同步网络请求不会继续。实现应使用可取消的异步请求，或在所有持久化点校验当前尝试身份。

## 9. 安全要求

### SEC-01 日志

以下内容不得以完整值写入普通日志、错误日志或诊断信息：

- `user_code`
- `device_auth_id`
- `authorization_code`
- `code_verifier`
- `code_challenge`
- Access Token
- Refresh Token
- ID Token
- 完整 Token 响应正文

本需求统一采用更严格规则：授权码完全不记录，而不是“允许记录截断值”。

### SEC-02 错误提示

普通用户错误提示不得包含：

- 内部异常堆栈；
- 完整 HTTP 响应正文；
- Token、授权码或 PKCE 内容；
- 可用于重放登录的请求字段。

### SEC-03 临时状态

登录成功、失败、取消、超时、离页或被新尝试替换时，应及时清理临时授权状态。一次性授权信息不得写入普通配置文件或明文数据库。

### SEC-04 凭据存储

长期 OAuth 凭据继续使用现有加密存储和刷新机制，不得因为新增设备码登录而降低安全性。

### SEC-05 已发现的相关安全缺口

实现时必须检查或隔离以下相关路径：

1. `OpenAIOAuthManager.exchangeCodeJson()` 当前会记录 Token 响应正文前 500 字符，并可能把完整响应正文放入异常；
2. `OAuthManager.sanitizeBody()` 尚未覆盖 `user_code`、`device_auth_id`、`authorization_code` 和 PKCE 字段；
3. `KimiOAuthManager` 当前会记录完整 `user_code`，因此其日志逻辑不能照搬；
4. 当前 Provider 显式导出会携带 Base64 编码的 OAuth Token JSON，Base64 不是加密。

本次设备码登录路径不得触发第 1、2 项中的敏感信息泄漏；若复用或修改这些代码，必须在本次一并修正并补测试。第 3 项只作为“不可照搬”的警示，本次不顺带修改 Kimi。

第 4 项是现有显式导出机制的独立安全议题。本需求按原稿的兼容性约束，不改变现有 OpenAI OAuth Provider 导入导出行为；是否整体调整 Token 导出，应另立需求完成安全与兼容性评估。

## 10. 兼容性要求

以下功能不得因本需求回归：

- OpenAI API Key 登录；
- OpenAI 浏览器回调登录；
- 手动 Bearer Token；
- 自定义 OpenAI 兼容 API 地址；
- OpenAI OAuth 自动刷新；
- OpenAI 模型列表和会话；
- Provider 添加、编辑、删除、退出登录和导入导出；
- 已保存的 OpenAI OAuth Provider；
- Anthropic、Gemini、xAI、Kimi、OpenRouter 等其他 Provider；
- 现有会话、工作区和 iOS 行为。

OpenAI OAuth 当前使用静态模型列表，因此“模型列表显示成功”不等同于已经真实调用 `/v1/models`。验收必须区分静态列表、真实模型请求和 Token 刷新。

## 11. 异常场景

实现和测试至少覆盖：

1. 请求用户码失败；
2. 必需字段缺失或为空；
3. 轮询间隔为空、非法或异常；
4. 用户长时间没有授权；
5. 用户主动取消；
6. 服务端拒绝或无法立即区分拒绝；
7. 网络中途断开或代理不可用；
8. 浏览器打开失败；
9. 用户只复制授权码但没有打开网页；
10. 多次点击登录；
11. 连续发起多个登录尝试；
12. 旧尝试晚于新尝试返回；
13. 切到后台、锁屏、旋转或 Activity 重建；
14. 等待过程中离开页面；
15. Token 交换成功但 Provider 保存失败；
16. Provider 保存成功但模型加载失败；
17. 设备码功能未启用或不支持；
18. 服务端协议或端点发生变化。

以上异常不得造成应用崩溃、永久加载、无效 Provider、半套凭据、任务相互覆盖或敏感信息泄漏。

## 12. 验收标准

### AC-01 正常登录

- 能选择 OpenAI OAuth 和设备码登录；
- 能看到登录网址和原样授权码；
- 能复制授权码和网址；
- 能通过按钮打开登录网页；
- 网页授权完成后应用自动继续；
- 登录成功后能保存 Provider；
- 能选择模型、创建会话并发起真实请求；
- 重启应用后登录状态仍有效；
- 凭据临近到期或到期后，现有自动刷新机制继续工作。

### AC-02 不依赖 localhost

设备码流程不访问 `http://localhost:...`，也不监听手机本地端口接收浏览器回调。

### AC-03 取消与竞态

- 取消会停止或使当前尝试失效；
- 可立即重新登录；
- 旧结果不能覆盖新结果；
- 主动取消不显示为失败。

### AC-04 超时

- 超过当前官方流程的等待上限后停止；
- UI 明确提示超时；
- 可以重新获取新授权码；
- 新旧尝试不会混淆。

### AC-05 网络异常

- 请求或轮询期间断网不崩溃；
- 页面不永久加载；
- 用户看到明确提示；
- 网络恢复后可以重试；
- 不保存不完整状态。

### AC-06 兼容性

- 现有 API Key、浏览器回调和手动 Bearer Token 正常；
- 已保存 OpenAI OAuth Provider 正常；
- 其他 Provider、导入导出、会话和工作区不受影响。

### AC-07 安全

- 自动化测试证明敏感字段被遮蔽或完全不进入日志；
- 取消、超时、失败和新尝试覆盖旧尝试时，不会持久化旧凭据；
- UI 错误不包含服务端敏感正文。

## 13. 测试边界

自动化测试应优先使用 Mock HTTP 响应，覆盖：

- 请求和响应解析；
- 轮询间隔与当前协议规定的等待上限；测试应允许缩短或注入时间，不能真实等待完整时长；
- 成功、继续等待、网络失败和功能未启用；
- 取消、重复点击和迟到结果；
- 日志脱敏；
- 凭据存储与清理；
- 现有浏览器登录回归。

测试策略已按 `D-06` 确认：

- 本地自动化以 Mock HTTP、单元测试、静态检查和构建验证为主；
- 不在本机启动 Android 模拟器；
- 不由 Codex 自动使用真实 ChatGPT 账号、workspace 权限或发起可能产生账户用量的真实模型请求；
- 真实登录、Token 刷新、模型请求、应用重启后持久化和真机生命周期由用户在真实 Android 设备上手工验收；
- Codex 在真机测试前提供检查清单，并在用户同意后协助分析脱敏日志；具体步骤到测试阶段再共同确认。

## 14. 初步实现边界（非最终方案）

当前最小改动方向是：

1. 为 OpenAI 增加独立的设备授权协议实现；
2. 复用 `OpenAIOAuthManager` 现有 Token 存储、账号解析和刷新能力；
3. 只参考现有 Kimi 设备登录的交互经验，实施 OpenAI 专用 UI，不修改 Kimi 协议或 UI 文件；
4. 将登录会话状态从一次性 Compose 局部状态提升到能够处理取消、迟到结果和必要生命周期的持有者；
5. 补充协议、状态、日志、竞态和回归测试；
6. 不引入完整 Codex CLI 或 app-server 作为 Android 运行时依赖，除非后续调查证明直接实现不可维护。

需求基线已经确认。产品代码必须按分阶段计划完成当前 Phase 的具体设计和门禁准备后再修改，不一次性跨越多个 Phase。

## 15. 需求决策

### 15.1 已确认

| 编号 | 已确认结论 |
|---|---|
| `D-01` | OpenAI OAuth 下显示两个明确按钮；设备码登录排在前面并标为“推荐”，但不自动开始 |
| `D-02` | 设备码只用于新建 Provider；不为已保存 Provider 增加设备码重新授权入口。极少数需要改用设备码的情况，由用户删除旧 Provider 后重新新建；接受旧 Provider 相关模型配置不自动迁移，以保持实现简单 |
| `D-03` | 默认使用系统 Custom Tab 打开授权页面，同时提供复制登录网址和复制授权码 |
| `D-04` | 临时断网时在总超时内有限重试和退避；连续失败后停止并明确提示，不无限重试 |
| `D-05` | 后台、锁屏、旋转和 Activity 重建后保持正确状态；系统彻底杀死进程后不恢复敏感临时授权信息，由用户重新发起登录 |
| `D-06` | 本地只做 Mock 自动化、静态检查和构建验证，不启动模拟器；用户负责真实 Android 设备验收，具体流程到测试阶段再讨论 |
| `D-07` | 登录成功但模型加载失败时，保留有效登录和 Provider，显示错误并允许单独重试，不回滚有效凭据 |
| `D-08` | 设备码仅用于官方 OpenAI/ChatGPT；自定义 OpenAI 兼容地址不显示设备码入口，继续使用 API Key 或手动 Bearer |
| `D-09` | 接受当前 Codex 设备授权端点和既有 client ID 可能变化的维护风险；端点应集中管理，并使用协议测试降低变更风险 |
| `D-10` | 服务端明确拒绝时立即停止；只有服务端无法区分等待与拒绝时，才继续等待到其他终止信号或总超时，不伪造服务端未提供的状态 |
| `D-11` | 登录成功但尚未保存 Provider 就离页或保存失败时，清理 pending instance 的临时凭据；只有 Provider 成功保存后才保留长期凭据 |
