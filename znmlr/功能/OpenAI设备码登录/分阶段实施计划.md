## 2. 当前态势与阶段策略

### 2.1 当前阶段

当前处于“Phase 7 交付收口”阶段：

- Phase 0～Phase 6 的需求、协议、安全、状态、UI、持久化、自动化和用户接受门禁已经通过；
- 可验证的 Debug APK 已从 Phase 5 产品提交构建，身份信息记录在 Phase 5 报告和 Phase 6 清单；
- 2026-07-30 再次核对官方 Codex `main`：设备授权端点形状、轮询状态和 15 分钟超时仍与实现一致；
- OpenAI/Codex 设备授权仍不是承诺稳定的标准 RFC 8628，后续维护仍需关注服务端变化；
- 用户已验证核心真机链路并明确接受 Phase 6；取消、断网、后台、锁屏、旋转、
  进程重建、删除后新建和自然 Token 刷新等未执行项继续保留为真机待验边界。

### 2.2 总体策略

不采用“一次改完协议、UI、凭据和生命周期，再统一测试”的方式。先建立安全和协议基础，再逐层接入状态、UI 和 Provider，最后进行自动化回归与真机验收。

局部优先突破点是：

1. 敏感日志和删除凭据清理；
2. 可由 JVM 单元测试验证的设备授权协议；
3. 可取消、可超时、不会被旧任务覆盖的登录状态协调器。

满足以上基础后，才把设备码入口接入新增 Provider 页面。

## 3. 全局实施规则

所有 Phase 都必须遵守：

1. 不直接在个人 `main` 上开发产品功能；
2. 先按 [个人派生仓库与官方上游同步说明](../../仓库维护/个人派生仓库与官方上游同步说明.md) 处理个人 Fork 和官方上游，再在 `feature/openai-device-code-login` 分支开发；
3. `origin` 用于保存个人分支，`upstream` 只用于获取官方更新，不向 `upstream` 推送；
4. 官方仓库不接受 Pull Request，本计划不包含向官方仓库创建 PR；
5. 每个 Phase 只修改该阶段必需文件，不顺带重构 Kimi、其他 Provider 或无关模块；
6. 每个通过验收的 Phase 使用详细中文提交说明，并推送到个人远端功能分支；
7. 发生上游冲突时保留现场，理解双方意图后人工解决并重新验证，不自动选择 `ours` 或 `theirs`；
8. 不在日志、提交、测试快照、截图或文档中保存授权码、Token、PKCE 或真实账号信息；
9. 本地不启动 Android 模拟器，不把 `connectedAndroidTest` 当作本地阶段门禁；
10. 真实 ChatGPT 登录和真实模型请求只能由用户在真机验收阶段主动执行；
11. 基线已有失败必须单独记录，不得伪装成新增功能通过或失败；
12. 任一安全、协议或数据一致性门禁失败时，停止进入下一 Phase。

## 6. Phase 1：安全与凭据清理基础

### 6.1 目标

先封住设备码流程必然经过的敏感日志和凭据清理缺口，为后续协议实现建立安全边界。

### 6.2 依赖

Phase 0 已通过。

### 6.3 实施计划

1. 扩展 `OAuthManager.sanitizeBody()`，覆盖：
   - `user_code`
   - `device_auth_id`
   - `authorization_code`
   - `code_verifier`
   - `code_challenge`
   - Access Token、Refresh Token、ID Token 和现有敏感字段；
2. 收紧 `OpenAIOAuthManager` 的 Token 交换日志和异常：
   - 不记录 Token 响应正文；
   - 不把完整响应正文放入普通用户可见异常；
   - 保留不含敏感信息的状态码和可操作错误分类；
3. 修正删除 OpenAI OAuth Provider 的清理路径：
   - 清除 API Key 镜像；
   - 清除加密 OAuth Token；
   - 清除该 Provider 的账号辅助字段和临时 PKCE 状态；
   - 不误删其他 Provider 的凭据；
4. 不顺带修复 Kimi 的现有日志；只确保新 OpenAI 路径不复制该行为；
5. 补充日志脱敏、异常消息和 Provider 删除清理的单元测试。

### 6.4 交付物

- OAuth 敏感字段脱敏修改；
- OpenAI Token 交换日志和错误收口；
- OpenAI OAuth Provider 删除凭据清理；
- 直接相关的 JVM 单元测试。

### 6.5 验收标准

- 单元测试证明所有新增敏感字段的完整值不会出现在脱敏输出；
- Token 交换成功和失败路径均不记录或抛出完整响应正文；
- 删除一个 OpenAI OAuth Provider 后，该实例的 API Key、Token、OpenAI 账号辅助字段和临时 PKCE 数据均不存在；
- 删除一个 OpenAI OAuth Provider 不影响其他 Provider 的凭据或行为；
- 现有浏览器 OAuth、退出登录和自动刷新接口继续编译；
- `OAuthLogRedactionTest` 及本 Phase 新增测试通过；
- `git diff --check` 通过；
- 本 Phase 独立提交，提交说明使用详细中文。

### 6.6 停止或回退条件

- 无法在不破坏其他 Provider 的情况下清除目标 Provider 凭据；
- 发现凭据键归属不清或存在跨 Provider 共用状态；
- 为通过测试必须扩大到无关认证重构。

出现以上情况时暂停，先补充设计，不把不完整安全修改带入 Phase 2。

## 7. Phase 2：OpenAI 设备授权协议核心

### 7.1 目标

实现不依赖 Compose、Activity 或真实账号的 OpenAI/Codex 设备授权核心，使协议行为能够在 JVM 上完整模拟。

### 7.2 依赖

Phase 1 已通过。

### 7.3 实施计划

1. 新增 OpenAI 专用设备授权协议模块，不复用 Kimi 的 RFC 8628 解析；
2. 集中管理当前 issuer、设备授权端点、设备登录网址、redirect URI 和 client ID；
3. 定义明确的数据模型：
   - 用户码请求结果；
   - 轮询中的继续等待；
   - 明确拒绝或终止；
   - 成功返回的授权码和 PKCE 数据；
   - 不支持、协议错误和网络错误；
4. 实现单次用户码请求：
   - 校验 `device_auth_id`、`user_code` 和 `interval`；
   - 校验最终展示的登录网址；
   - 不修改 `user_code` 的格式；
5. 实现单次轮询请求和响应分类：
   - 只按当前官方行为解释响应；
   - 不能把普通等待伪造成授权拒绝；
   - 区分初始请求的“不支持”和轮询中的“继续等待”；
6. 实现成功后的授权码到 OAuth Token 交换，并复用现有安全凭据数据模型；本阶段只返回内存中的凭据结果，不写 Provider 或长期凭据存储；
7. 对 HTTP 客户端提供可注入边界，并使单次请求能够被取消；
8. 所有协议异常只携带脱敏诊断信息。

本 Phase 不实现持续轮询循环、轮询间隔调度、总超时或网络退避；这些行为由 Phase 3 的登录协调器统一负责。

### 7.4 交付物

- OpenAI 设备授权数据模型；
- OpenAI 设备授权 HTTP/协议实现；
- 集中的端点和协议配置；
- MockWebServer 和纯逻辑单元测试。

### 7.5 验收标准

- 正确解析完整用户码响应；
- 必需字段缺失、为空、格式异常或间隔异常时安全失败；
- `user_code` 原样传递，不假设长度、大小写或连接符；
- 初始请求明确不支持时返回可识别结果；
- 单次轮询的等待响应被分类为“继续等待”，不被误判为失败；
- 明确终止、网络异常、非预期状态码和无效 JSON 均有确定分类；
- 成功响应能得到 Token 交换所需的授权码和 PKCE 数据；
- Token 交换结果包含现有 `OAuthManager.validAccessToken()` 保存和自动刷新所需的数据，并有兼容性测试；
- 单次 HTTP 请求能够取消；
- 请求、响应、异常和测试输出均不包含完整敏感字段；
- 测试不访问真实 OpenAI 服务。

### 7.6 停止或回退条件

- 官方 Codex 协议在实施期间变化；
- 现有 client ID 或端点无法在目标应用语境中使用；
- Mock 行为与官方源码不能对应；
- 必须引入完整 Codex CLI/app-server 才能正确工作。

发生以上情况时回到需求与协议调查，不继续接入 UI。

## 8. Phase 3：登录状态、并发与生命周期

### 8.1 目标

建立单一有效登录尝试、可靠取消、有限重试和迟到结果保护，使 UI 只负责展示状态。

### 8.2 依赖

Phase 2 已通过。

### 8.3 实施计划

1. 定义与需求状态对应的内部状态机；
2. 为每次登录创建不可混淆的本地身份；
3. 新尝试开始时取消或使旧尝试失效；
4. 在网络响应、Token 交换和持久化前检查当前尝试仍有效；
5. 使用 Phase 2 的单次协议操作实现完整轮询协调：
   - 主动取消；
   - 按服务端间隔调度下一次轮询；
   - 当前协议规定的总超时；
   - 临时网络错误的有限重试和退避；
   - 连续失败后的明确终止；
   - 旧请求晚于新请求返回时丢弃旧结果；
6. 将状态持有者放在能够承受 Compose 重组、旋转和 Activity 重建的位置；
7. 后台和锁屏返回后保持正确状态；
8. 系统彻底杀死进程后不持久化授权码、设备授权 ID 或 PKCE，重新进入时回到安全的未登录状态；
9. 仅取消 Compose `Job` 不视为充分取消；网络调用应可取消，持久化点仍需身份校验。

### 8.4 交付物

- 登录状态模型和协调器；
- 取消、超时、重试和竞态处理；
- 可注入调度器、时间和网络边界；
- 协程与状态机单元测试。

### 8.5 验收标准

- 同一新增 Provider 同时最多一个有效设备码登录尝试；
- 连续点击不会创建多个并行有效任务；
- 取消后停止或使网络结果失效，并立即允许新尝试；
- 旧任务任何迟到结果都不能更新 UI 或写入凭据；
- 超时后停止轮询、清理临时状态并允许重新获取新码；
- 临时断网只做有限重试，不永久加载；
- 连续失败进入明确错误状态；
- 逻辑级测试证明同一状态持有者被重新订阅时不会重复启动请求，并证明重建协调器时不会从 Bundle、`SavedStateHandle` 或磁盘恢复敏感状态；
- 模拟进程重建时不会恢复敏感临时字段；
- 协程虚拟时间测试不需要真实等待协议完整时长。

本 Phase 的生命周期验收只是 JVM 逻辑级暂验，不能据此宣称真实后台、锁屏、旋转或 Activity 重建已经通过；真实 Android 生命周期只在 Phase 6 由用户真机验收。

### 8.6 停止或回退条件

- 状态持有者必须把敏感码写入持久化 Bundle 或普通数据库才能工作；
- 取消无法阻止旧结果持久化；
- 测试依赖真实网络或真实时间。

出现以上情况时不得进入 UI 集成。

## 9. Phase 4：新增 Provider UI 与持久化集成

### 9.1 目标

只在新增官方 OpenAI Provider 流程中接入设备码登录，并完成安全的凭据保存和模型加载。

### 9.2 依赖

Phase 3 已通过。

### 9.3 实施计划

1. 在新增 OpenAI Provider 页面显示两个明确入口：
   - 设备码登录，排在前面并标为推荐；
   - 现有浏览器回调登录；
2. 不在已保存 Provider 详情页增加设备码重新授权入口；
3. 自定义 OpenAI 兼容地址不显示设备码入口，继续使用 API Key 或手动 Bearer；
4. 新建设备码等待界面，显示：
   - 登录网址；
   - 原样授权码；
   - 打开登录网页；
   - 复制登录网址；
   - 复制授权码；
   - 当前状态；
   - 取消；
5. 默认通过系统 Custom Tab 打开网页，同时保留复制能力；
6. 复制网址或授权码后提供明确反馈；
7. 普通用户文案不暴露 OAuth、PKCE、Access Token 或 Refresh Token 等内部术语；
8. 登录成功后：
   - Token 结果在用户保存 Provider 前只保留于内存；
   - 不通过 Bundle、`SavedStateHandle`、普通配置文件或数据库保存临时 Token；
   - 只在当前尝试仍有效且用户确认保存时提交 Provider 和长期加密凭据；
   - 跨 Provider 配置和加密凭据两套存储提交前，写入只包含 instance ID 和提交阶段的非敏感 pending-commit 标记；
   - 提交成功后清除标记；应用启动时若发现未完成标记，按阶段协调清理半套 Provider 和凭据，或确认两侧均完整后结束提交；
   - pending-commit 标记不得包含 Token、授权码、设备授权 ID 或 PKCE；
   - 允许用户保存 Provider；
   - Provider 保存成功后保留长期凭据；
   - 保存前离页时直接丢弃内存凭据；
   - Provider 或凭据任一步保存失败时执行补偿清理，不留下半套 Provider 或孤立凭据；
9. 模型加载失败时保留有效登录和 Provider，显示错误并允许单独重试；
10. 保持浏览器 OAuth、API Key、手动 Bearer 和其他 Provider 行为不变；
11. 实现 OpenAI 专用 UI，不修改 Kimi 协议或 UI 文件；
12. 新增默认英文和简体中文字符串资源，其他语言在未翻译时安全回退到默认文案。

### 9.4 交付物

- 新增 Provider 页面双登录入口；
- OpenAI 设备码等待 UI；
- Custom Tab、打开与复制交互；
- Provider 保存、pending 凭据清理和模型加载集成；
- UI 状态转换和持久化逻辑测试。

### 9.5 验收标准

- 设备码只出现在新增官方 OpenAI Provider 流程；
- 已保存 Provider 详情页没有新增设备码重授权入口；
- 自定义 OpenAI 兼容地址没有设备码入口；
- 设备码和浏览器登录入口清楚区分，手动 Bearer 不与设备码混淆；
- UI 原样显示授权码和登录网址；
- 打开、复制网址、复制授权码和取消操作均有明确状态结果；
- UI 不显示 Token、PKCE、完整服务端响应或内部堆栈；
- 登录成功但保存前离页不会遗留 pending 凭据；
- 保存失败不会留下无法管理的有效凭据；
- 保存前的 Token 只存在于当前内存状态，进程死亡后不可恢复；
- 自动化测试覆盖跨存储提交的每个可中断阶段；应用重启后能够利用非敏感标记清理或完成一致状态；
- 模型加载失败不会回滚已经保存的有效登录；
- 保存的 Token 数据能够继续进入现有自动刷新路径；
- 原浏览器 OAuth、API Key、Bearer 和 Kimi 相关代码通过编译及直接相关回归测试；
- Kimi 文件没有改动；
- 本阶段不要求模拟器或真实账号；视觉和系统浏览器行为留到 Phase 6。

### 9.6 停止或回退条件

- UI 必须修改 Kimi 协议才能实现；
- 新旧登录任务仍可能覆盖；
- Provider 保存边界无法保证凭据一致性；
- 为显示设备码必须改变自定义 OpenAI 地址的既有行为。

### 11.4 真机测试场景

1. 正常设备码登录：
   - 新增官方 OpenAI Provider；
   - 获取网址和授权码；
   - 复制授权码和网址；

2. 不依赖 localhost：
   - 设备码流程不访问或监听手机本地回调端口；
3. 取消和重新开始：
   - 等待时取消；
   - 立即重新发起；

4. 网络异常：
   - 请求码或等待期间临时断网；

5. 生命周期：
   - 切后台后返回；
   - 锁屏后解锁；
   - 旋转屏幕；
   - 系统重建 Activity；
6. Provider 持久化：
   - 保存 Provider；
   - 关闭并重启应用；
   - 登录状态仍有效；
7. 模型和会话：
   - 选择模型；
   - 创建会话；
   - 在用户同意产生账户用量后执行最小真实请求；
   - 如果用户愿意且可以安全触发，观察 Token 自动刷新；无法在验收窗口触发时，明确记录为“自动化刷新验证通过，真机刷新待长期观察”；
8. 兼容性抽查：
   - 现有浏览器回调入口仍可见；
   - API Key 和手动 Bearer 入口正常；
   - 已保存 Provider 不出现新的设备码重授权入口；
9. 删除后新建策略：
   - 删除 OpenAI OAuth Provider 后旧凭据被清理；
   - 如需验证改用设备码，重新新建 Provider，不要求迁移旧配置。
