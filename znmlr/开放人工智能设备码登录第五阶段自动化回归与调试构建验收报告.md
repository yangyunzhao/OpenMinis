## 3. 关键实现

### 3.1 复用既有 OAuth 刷新语义

设备码登录保存的结构化 Token 继续通过既有 `OAuthManager.validAccessToken()` 和 `refreshToken()` 路径使用，没有为设备码另建一套运行期认证旁路。

刷新判断保留既有四小时窗口：

- 距离过期时间严格小于四小时时尝试刷新；
- 恰好等于四小时时不提前刷新；
- Token 仍未过期而刷新失败时，继续返回当前 access token；
- Token 已过期且刷新失败时，只有在确认存储快照未被其他并发调用更新后才清理凭据。

手动 Bearer Token 的既有优先级保持不变。

### 3.2 刷新请求与响应处理

刷新请求使用标准的 `application/x-www-form-urlencoded` 表单，发送：

- `grant_type=refresh_token`；
- 当前 `refresh_token`；
- `client_id`；
- 仅在配置存在时发送 `client_secret`。

刷新响应必须同时满足：

- HTTP 状态码为 2xx；
- 响应可解析为 JSON；
- 返回非空 `access_token`。

响应省略或返回空 `refresh_token` 时保留原 refresh token；省略或返回空 `id_token` 时保留原 ID token，避免普通 access-token 刷新破坏设备登录保留的令牌元数据。

`expires_in` 使用同一次传入时钟换算为绝对 `expire_at`，并对乘法及加法溢出进行饱和保护。保存时直接持久化已经计算完成的绝对过期时间，不使用第二次系统时钟重复换算。

### 3.3 并发和取消安全

同一个 Provider 实例的 access-token 判定与自动刷新由实例级 `Mutex` 串行：

1. 第一个调用进入临界区并执行刷新；
2. 后续调用等待锁；
3. 后续调用取得锁后重新读取落盘快照；
4. 如果 access token、refresh token 或过期时间已经变化，直接使用新快照，不再发起重复刷新。

刷新失败后的清理也会重新比较 access token、refresh token 和过期时间。只要任一字段已被其他调用更新，就保留最新凭据，避免失败调用误删并发成功刷新得到的结果。

OkHttp `Call` 通过可取消挂起桥接到协程：

- 协程取消会取消底层 HTTP Call；
- 取消异常继续向上传播，不被普通网络失败处理吞掉；
- 迟到响应会关闭，避免响应体泄漏；
- 请求、响应解析和加密存储写入固定在 `Dispatchers.IO`，不在调用者线程执行阻塞 I/O。

### 3.4 日志与敏感信息边界

刷新失败只记录固定的通用错误，不记录响应正文，也不把 access token、refresh token、ID token、PKCE 或其他授权材料加入新增日志。

本阶段的网络验证全部使用本地 `MockWebServer` 和合成 Token；没有连接真实 OpenAI 授权端点。
