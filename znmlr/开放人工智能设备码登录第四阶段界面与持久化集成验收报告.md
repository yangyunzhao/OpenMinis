# OpenAI 设备码登录第四阶段界面与持久化集成验收报告

## 1. 结论

Phase 4 已通过本地门禁，可以进入 Phase 5。

本阶段把 Phase 2/3 的协议核心和状态协调器接入“新增 OpenAI Provider”页面，
完成双登录入口、设备码交互、路由级生命周期、跨存储一致性提交、崩溃恢复、
模型准备及兼容性保护。

本结论只覆盖 JVM、Android Debug 编译和静态审查。Custom Tab 的实际显示、
系统浏览器返回、旋转、后台、锁屏、Activity/进程重建和真实账号授权仍必须由
用户在 Phase 6 的真机上验收。

## 2. 实施范围

### 2.1 UI 与生命周期

- 只在新增官方 OpenAI OAuth Provider 时显示设备码入口；
- 设备码入口排在原浏览器 OAuth 之前，并标为推荐方式；
- 原浏览器 OAuth 和手动 Bearer 入口保留；
- 自定义 Base URL 不提供设备码登录；
- 三种登录路径在活动期间相互禁用，避免并发提交；
- 新增专用设备登录对话框，支持：
  - 原样显示登录网址和一次性授权码；
  - 分别复制网址和授权码并显示明确反馈；
  - 使用 Android Custom Tab 打开登录网址；
  - 浏览器打开失败时显示固定、安全的提示；
  - 用户取消等待；
- 自动打开浏览器的一次性 claim 在 `LaunchedEffect` 内消费，避免被放弃的
  Compose composition 吞掉；
- ViewModel 绑定 `ADD_PROVIDER` 的 `NavBackStackEntry`，路由离开和
  `onCleared()` 会取消任务；
- wizard 步骤、Provider 类型、凭据类型、标签及非敏感配置使用可恢复状态；
  Token、授权码、设备授权 ID、PKCE 和错误正文不进入 `rememberSaveable`、
  Bundle 或导航参数。

### 2.2 Provider 与凭据提交

新增窄接口提交器，并固定设备登录创建的 Provider 形态：

```text
providerType = openAI
credentialType = oauth
customBaseURL = null
```

提交顺序为：

1. 写入只含随机 instance ID 和阶段名的 `PREPARED` marker；
2. 严格保存 Provider 到 Room 和兼容 JSON mirror；
3. 更新为 `PROVIDER_SAVED`；
4. 原子写入结构化 OAuth Token，并同步 access-token API-key mirror；
5. 验证目标 Provider 仍与本次提交一致；
6. 完成 attempt generation 握手；
7. 写入 `COMMIT_CONFIRMED` 并清理 marker；
8. 释放本地事务锁后应用 OpenAI OAuth 静态模型。

Provider、凭据、marker 和 generation 握手的本地写入阶段由同一
`providerMutationMutex` 串行化。所有会整体保存 Provider 配置的 Provider、
ModelEntry、ModelGroup、AgentLoop、默认 Group、语音 Group 和导入入口遵守
相同的 `providerMutationMutex -> configLock` 锁序；模型请求完成时若 Provider
已被删除，结果会被丢弃，不能生成孤立 ModelEntry。

### 2.3 失败补偿与启动恢复

- 任一最终确认前失败或取消都会尝试清理 Provider、结构化 OAuth Token 和
  API-key mirror；
- 补偿全部成功后才清 marker；补偿失败会保留 marker，供下次冷启动重试；
- 持久层补偿失败时，当前进程仍会先从 StateFlow 隐藏半提交 Provider；
- `COMMIT_CONFIRMED` 只有在 Provider、结构化 Token 和 API-key mirror
  完整且 access token 匹配时才会最终保留；
- marker 指向其他类型 Provider 时只清 marker，不删除用户 Provider；
- marker 存储整体不可读时配置加载失败关闭，不发布未经恢复的基础快照；
- 单笔恢复异常时保留 marker，并在本次内存快照中隐藏目标官方 OAuth
  Provider；
- 启动加载与恢复为 single-flight，新的 `PREPARED` 必须等待旧恢复完成。

marker 不保存 Token、用户码、设备授权 ID、authorization code、PKCE、标签、
账号或响应正文。

### 2.4 模型与既有功能兼容

- 新建设备登录首次准备模型时直接应用静态 OpenAI OAuth 模型，不产生真实
  `/v1/models` 请求；
- Provider 已提交但模型准备失败时保留有效登录，允许只重试模型准备；
- 既有 OpenAI OAuth 的普通模型刷新仍保持原顺序：先进入
  `validAccessToken()` 自动刷新及 API-key mirror 同步，再应用静态模型；
- API Key、原浏览器 OAuth、手动 Bearer 和 Kimi 文件未改为设备提交协议；
- 删除 OpenAI OAuth Provider 时会清理设备 Token、manual Bearer、
  browser OAuth 辅助字段和 API-key mirror。

## 4. 审查中发现并修复的关键问题

1. manual Bearer 逻辑 key 名不一致，可能让旧 Bearer 优先于新设备 Token；
2. 新 `PREPARED` 可能与启动恢复竞争；
3. Room 成功、mirror/规范化失败后可能留下 Provider 孤儿；
4. 配置加载或恢复异常可能永久悬挂，或错误发布空/半成品配置；
5. 严格本地 I/O 可能运行在主线程；
6. 保存取消、旧 attempt 和新 attempt 复用同一 Provider ID 的竞争；
7. Custom Tab 自动打开标志在 composition 提交前被消费；
8. 删除/更新和跨存储提交可交叉；
9. 补偿持久化失败时半提交 Provider 仍可在当前进程可见；
10. 其他整表配置写入口可能用陈旧快照复活半提交 Provider；
11. Provider 删除后迟到的模型结果可能创建孤立 ModelEntry；
12. 既有 OpenAI OAuth 模型刷新顺序一度绕过自动 Token 刷新。

上述问题均已在最终工作区关闭，并完成重新编译与聚焦/完整回归。

## 5. 未执行验证与剩余风险

本阶段没有执行：

- Android 模拟器；
- `connectedAndroidTest`；
- 真机安装和视觉检查；
- 真实 ChatGPT/OpenAI 登录；
- 真实 Token 刷新；
- 真实模型请求。

原因：这些项目按已确认边界留在 Phase 6，由用户在真实设备上决定账号、网络
及是否产生真实账户用量。

仍待观察：

- 官方设备授权端点不是承诺稳定的公开集成 API；
- Android 深度睡眠和厂商后台限制对 15 分钟 wall-clock 体验的影响；
- 启动恢复生产适配器的真实进程强杀场景只能在真机验收；
- marker 只允许 ID 和阶段名，因此把 marker 存储视为应用内部可信日志；损坏
  marker 指向另一条同形官方 OAuth Provider 的极端情况无法仅凭这两个字段
  证明归属；
- OpenAI 自动刷新需要在 Phase 5 用模拟过期 Token 和 Mock 刷新响应补充
  端到端纯 JVM 回归。
